Read-only inspection of the actual queue found two pending commands in one notification: CREATE_2D resource 2, format 2, 800x600, then ATTACH_BACKING with 65 entries totaling 1,921,024 bytes. Entry 63 spans 1,179,648 bytes. The virtio memory-entry length is a 32-bit byte count; its length is separate from the bounded control-message descriptor. See the [OASIS virtio-GPU protocol](https://docs.oasis-open.org/virtio/virtio/v1.2/virtio-v1.2.html).

This actual entry becomes 1,048,576 plus 131,072 bytes, so the existing device-state list grows from 65 to 66 entries: 16 additional serialized metadata bytes. There is no new RAM or pixel copy during attachment. Every original small entry remains identical. The original normalized 2,048-entry bound stays, and the entire incoming RAM range is validated before metadata publication. Invalid zero, out-of-RAM or excessive normalized mappings roll back the complete native instruction.
